- **Date:** 2026-11-14. **Status:** accepted by Claude as technical design (autonomous lane). Open to change by the project lead. Bead dreamcounter-9c8980 (P4.2). Follows D11 (doc-d9s) and D18 (doc-g97). The prompt text is a research choice the project lead may want to change (see "Prompt").
- **Decision:**
  1. **Two servers.** `dc-mcp --state-dir <dir>` is the operator's server. `dc-mcp --state-dir <dir> --proposer <run>` is a proposer's server. It serves one run, which must exist, and has two tools: `dc_next_batch(worker)` and `dc_submit(worker, batch, token, programs, model?)`. A proposer cannot list runs, name another run, or see a library size, a frontier, or a result. The operator's server gains `dc_proposal_stats(run)` and `dc_check_pending(run)`, which runs the pending checks and reports how many still wait and which batches another server holds the claim for (`claimed_elsewhere`). And `dc_run_status` reports batches and the current iteration's counts.
  2. **A batch is one task.** It asks for `programs_per_batch` programs (a run setting, 1 by default, so each program comes from its own batch: D11 requirement 3). A task needs `proposals_per_task` programs in each iteration. `dc_next_batch` gives the task with the most open slots, the earliest in the run's order on a tie. Open slots are the quota less the programs received and the programs held by live leases. A batch asks for at most 32 programs, the most a submission may hold. A worker that holds a batch with a live lease gets no other until it submits, so one proposer cannot hold every slot. The wait says when the lease ends. A proposer that lost its payload waits until then.
  3. **Leases.** A batch is held for `lease_seconds` (a run setting, 1800 by default). After that its slots can be handed out again. A submission after the lease, in the same iteration, is still checked and counted: its programs are real samples. When no slot is open, `dc_next_batch` returns no batch, a reason, and when to ask again.
  4. **Events.** `BatchIssued` holds the batch number, iteration, task, programs wanted, worker id, token, issue time, deadline, and the payload, which reads back as it was sent. The parts of a prompt that many batches share are stored once, in `PromptStored` events in the same commit, and the payload names them; the batch number and token, and the solved programs, are written out in each event (dreamcounter-20c6e5, D18 item 17). So a proposer sees the same payload as before, and every payload it was sent can be read back from the journal byte for byte. `Submitted` holds the batch, the worker id, the token it gave, the iteration it came in, the time, the model the proposer named, the programs as they were sent, and the standing. `Checked` holds the batch, the library length the checks used, and one check for each program. The state keeps the batches, counts for each task and iteration, byte counts for each iteration, and the verified programs that no iteration step has taken yet, which P4.4b gives to dc-driver. No event holds a floating-point number.
  5. **Tokens and standing.** Each batch has a 128-bit random token from the operating system. It is sent only in the batch's payload, and `dc_submit` must give it. A submission with the wrong token, or from a worker other than the one the batch went to, is foreign: it is kept, not checked, and the batch stays open. The reply is an error that says the token or worker does not match; it says nothing about the programs. The first submission to arrive from the batch's worker is on time or expired, and is checked. A submission after the batch's iteration ended is late: it is kept, not checked, and not counted. A later submission for the same batch is a repeat: it is kept and not checked. Submissions that are not checked are kept up to a cap for each batch (dreamcounter-9fa01a): `max_unchecked_per_batch` (a run setting, 3 by default) foreign ones, and as many late or repeat ones from the batch's worker. A submission past the cap is refused: its programs are not kept, and the store adds one to a count for its iteration and kind in the file `refused` beside the journal (D18). The reply is an error that says the submission is counted but not kept. `dc_proposal_stats` and `dc_run_status` show the counts as `refused_repeats` and `refused_foreign`. A late submission is the first from its worker, so it is never refused. The cap is the server's rule, not the journal's: `Submitted` events past it still apply, so a journal written before the cap replays as before, and a run made before the setting has the default. A request for a batch the run never issued, or over the size limits (32 programs, 64 KiB a program, 200 bytes for a worker id or model name), is a tool error, and nothing is written.
  6. **Checks.** A program is surface syntax (spec §10) that defines `solve`. The prelude is in scope, and library entry `i` is in scope as `fn_i`. The stages are compile (parse, desugar, `solve` defined), type (the task's signature, with prelude and library schemes), and run (every example, with the harness's example fuel, after the prelude and then the library are expanded). A program that passes is kept as a core s-expression with its prelude and library references in place, so Stitch sees `map` as a token (spec §10). Error text is cut at 2000 bytes. A panic while checking is recorded as a run failure.
  7. **Submissions are kept first and checked afterwards.** `dc_submit` commits the `Submitted` event and replies. The proposer server then checks pending submissions in a background task, oldest first, without the run's lock. It commits `Checked` only to the journal it read the submission from (a run removed and made again under the same name has a new journal), only if the submission still waits with the programs it checked, and only if the library length has not changed; otherwise it checks again with the new library. A `Checked` event with another library length is refused. Each check is claimed first, so that several servers check different submissions and each one once (dreamcounter-866f39). The claim is a non-blocking exclusive `flock` on the file `checks/<batch>.lock` in the run's directory, held while the programs run. A checker skips a submission whose claim another holds and takes the next one, so it does not wait for another server's check. The operating system releases a claim when its holder stops or is killed. A holder that is done removes the file before it lets go, if the file at the path is still the one it locked, and a claim counts only on the file that is at the path once the lock is held. A file left by a holder that stopped is taken by the next checker of that batch, or removed by the next check once the batch is checked. The journal does not depend on these files. A proposer server also starts its checks when it answers `dc_next_batch` with a wait and its checks are not running, so a check whose claimant stopped is taken up while proposers wait for it. An iteration cannot finish while checks are pending, and `quota_in` waits for them. `IterationFinished` says how many verified programs the iteration step took, counted from the first. The step reads the verified programs and commits this event later, without the run's lock in between. A program checked in that time stays verified, and the next step takes it. An event that names more programs than are verified is refused. A panic in a background check is logged and retried, as an error is. After an error the background checks wait and then try again: 5 s at first, twice as long after each wait that runs its full time, up to 300 s. A new submission ends such a wait at once, so its check is done without waiting out the rest once the cause has cleared (dreamcounter-eb6187). It does not shorten the next wait: while the cause lasts, each submission costs one more try. A `dc_next_batch` wait does not end the wait: proposers poll about once a second while checks are pending, and a lasting error would then cost a try at each poll. The waiting thread holds no lock of the run, and the server does not wait for it when it stops.
  8. **The blind arm.** The reply to every submission is the batch number and how many programs came in. It does not depend on the programs, and it does not wait for the checks. A later reply can still be slower while a background check runs. A proposer is told why a request was refused only when the request is at fault. For a busy run it is told to ask again. For any other failure of the store or the server it gets a reply that names no path and no state, and the detail goes to the server's standard error.
  9. **Prompt.** The payload is JSON: the batch number, the token, the programs wanted, the lease in seconds, and a prompt. The prompt has the instructions, a short guide to the language, the type of each primitive and prelude function (taken from the code), the library with types and bodies in surface syntax, up to three programs that solve other tasks (the first member of each frontier, chosen by the run's seed and the batch number), and the task's description, signature, and examples. It does not show task names, costs, or anything about earlier submissions. It does not ask for efficient programs.
  10. **Journal format 2.** The events changed, library entries gained an arity (as in dc-driver), and the log kinds for payloads, submissions, and evaluations went. A version 1 journal is refused with the "other format version" error. No run was started in version 1 (D11 requirement 5).
- **Alternatives:**
  - (a) One server with a role check in each tool. The proposer would still see the operator's tools listed.
  - (b) A batch of several tasks. Samples written in one context are correlated (D11 requirement 3).
  - (c) Payloads and submissions as log records of the P4.1 kinds. `dc_next_batch` and the quota check would then have to read the log.
  - (d) Count a submission after its lease only if its slots were not handed out again. That drops real samples; counting them only lets a task get more than its quota.
  - (e) Refuse late submissions. D11 needs every submission logged.
  - (f) Store the program with the prelude expanded, so dc-driver can read it today. Stitch would then see the prelude's bodies.
- **Limits:**
  - **dc-driver does not read prelude references yet.** Bead dreamcounter-6b1cd9.
  - **Prelude references are ids** (`lib_4294901760`...). A change to the prelude's order changes what a stored program means.
  - **A run records task names only**, so a changed corpus is not noticed (D18). The payload in the journal shows the description and examples that were sent.
  - **A proposer server builds a verifier once for each library length** (dreamcounter-98f1c6). A verifier loads the prelude and the library. The server keeps one verifier, for the longest library it has seen. It uses that verifier only when the run's library under the lock is the one it was built for. `dc_next_batch` builds a missing verifier without the run's lock and tries again; if the library grew in the meantime, it builds the verifier under the lock. Checks run on a clone of the kept verifier. A background check and `dc_next_batch` that miss at the same moment can each build one, so a length is usually built once, not always. Each server process builds its own, and `dc_check_pending` on the operator's server builds one for each call.
  - **A library entry that does not load stops every check.** The submissions stay kept and pending, so the iteration cannot finish. The error goes to the proposer server's stderr only. The operator sees it as `pending_checks` that stay above zero.
  - **Checks run in the background only in a proposer server.** If the server stops before it checks a submission, the submission waits until a proposer server answers `dc_next_batch` with a wait or takes a submission, another proposer server starts, or the operator calls `dc_check_pending`. `dc_check_pending` leaves a submission that another server is checking to that server.
  - **A claim held by a process that hangs holds up its submission.** A holder that is stopped (SIGSTOP) or blocked on a hung file system keeps its claim, and no other checker takes the submission. `dc_check_pending` names such batches in `claimed_elsewhere` and has no way to force them. The fix is to kill the holder: its claim goes with it, and the next check takes the submission.
  - **Claims need a local file system**, as the run's lock does (D18). On NFS, Linux emulates `flock` with POSIX locks, which belong to a process, so two checkers in one process would both get a claim.
  - **Proposers must not read the state directory.** The journal holds every token and every check result as written. A proposer with shell access to the state directory could read them; the blind arm and the tokens both depend on proposers having no such access.
  - **Worker ids are free-form.** The one-batch rule limits a proposer under one id. A proposer that uses many ids can still lease every open slot. Tokens stop it taking a batch it was not sent, not from holding slots.
  - **A lost payload costs up to one lease.** The payload is not sent again, so a proposer that lost it waits for the lease to end (1800 seconds by default). If that batch's task is the last one short of its quota, the iteration waits as long.
  - **The cap bounds the journal for each batch, not for each run.** A batch can add at most `2 × max_unchecked_per_batch` unchecked submissions, each up to 32 × 64 KiB. Foreign submissions can name any batch ever issued, so the bound grows with the batches.
  - **An empty submission reopens its slots.** A proposer that asks for a batch and submits no programs, again and again, gets a new batch each time. Nothing bounds this loop. A proposer that gives up on a task does the same, and the project lead chose not to change what such a proposer gets (dreamcounter-20c6e5). Since the prompt is stored once, a round stores the batch's own text and the submission, not the prompt again: in the test, with an empty library, a round adds about 600 bytes where it added about 9,100. The journal still grows with each round, and the solved programs a payload shows are written out each time.
  - **Refusal counts are outside the journal.** The `refused` file is not part of the state, so a copy of a run without it loses the counts, and a run that is made again under the same name starts from none (the file holds the journal's id).
  - **A second timing path.** While the last programs an iteration needs are being checked, `dc_next_batch` says so. A proposer that polls learns how long the checks took, though not what they found.
  - **Refused requests are not logged.** A submission for a batch the run never issued, or over the size limits, writes nothing.
  - **Clock.** Leases use the server's wall clock. Servers on one machine share it.
  - **A request line over 16 MiB gets no reply** (dreamcounter-62f7f3). A full submission is under 2.1 MB; a payload grows with the library.
