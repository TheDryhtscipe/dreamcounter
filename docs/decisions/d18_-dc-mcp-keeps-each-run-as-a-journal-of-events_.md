- **Date:** 2026-11-14. **Status:** accepted by Claude as technical design (autonomous lane). Open to change by the project lead. Bead dreamcounter-50338f (P4.1). Follows D11 (doc-d9s).
- **Decision:**
  1. **State is a fold of events.** A run's state (`RunState`: config, task set, library, per-task frontiers, iteration number, log counts) changes only by applying an `Event`. The events on disk are the whole state.
  2. **One journal file for each run.** `<state-dir>/<run>/journal` has a header line and then one line for each commit: `<number> <CRC-32> <JSON array of events>`. The header holds the format version and a random id: `dc-mcp journal 1 <16 hex digits>`. The events of one commit take effect together.
  3. **A commit is on disk before it is acknowledged.** `Store::commit` applies the events to the state it holds, appends one record, and calls `fsync` before it returns. A rejected event leaves the state unchanged, so if the first event is rejected the store keeps its state. If a later event is rejected, or the write fails, the store drops its state, and the next operation reads the journal again. So a commit does not copy the state (dreamcounter-3c6fca). A commit over a torn tail still checks the events against a copy first, so that a rejected commit sets no tail aside. If the write or the `fsync` fails, the store cuts the record out again. If that fails too, it returns a separate "outcome unknown" error. `create_run` returns the same error when the journal is in place and the sync of its directory fails.
  4. **Torn tail.** A write that did not finish can leave anything after the last good record: part of a line, or a whole line with wrong bytes. Bytes after the last good record are a torn tail when no record with a right checksum follows them on a later line. Reading ignores a torn tail. The next commit copies it to a file `torn-<offset>-<n>` beside the journal and writes in its place.
  5. **A set-aside tail is reported in the run.** The commit that replaces a tail puts a log record of kind `Recovery` first in its own record, in the iteration the run is in. `dc_run_status` shows the count. The store also writes a line on standard error, and a failure of that write is ignored.
  6. **A failed commit puts the tail back.** If the commit that replaces a tail fails, the store writes the tail back to the journal, so the next commit sets it aside and reports it. If it cannot write the whole tail back, it cuts the part out again. A tail is not set aside again when a plain file `torn-<offset>-<n>` already holds the same bytes. The store passes over any other entry under such a name and takes the next number. Of the run's records, the store deletes one thing only: a side file that it could not finish writing. It also removes the empty claim files of checks under `checks/` (D20, dreamcounter-866f39), which hold nothing the run needs.
  7. **Corruption.** Damage with a good record on a later line is corruption. So is a record with a right checksum whose number is out of order, or whose events do not parse or do not apply. The store then refuses the run and does not change the file.
  8. **Several server processes can share a run.** Each client session starts its own stdio MCP server, so two sessions give two processes on one state directory. Each operation takes an exclusive lock (`flock`) on the run's directory, reads the records other processes added, and then acts. It waits 30 seconds for the lock and then fails with a "busy" error.
  9. **A lock counts only on the directory at the run's path.** After it takes the lock, a commit or `create_run` checks that the directory it locked is still the one at the run's path (device and inode). If the directory was replaced, the operation fails with a "replaced" error and writes nothing.
  10. **A store checks its memory against the journal.** Before a store uses the state it holds in memory, it checks the journal's id and the last record it read. Another id means the run was removed and made again, and the store reads the new journal from the start. The same id with a shorter journal or a changed last record is corruption, reported once. The next operation reads the journal from the start.
  11. **Tool calls run off the protocol thread.** A call that waits for a lock does not hold up `ping`, other tools, or other runs.
  12. **A tool reports the state its own commit made.** `Store::commit_then` runs a closure on the state after the events, under the same lock. `dc_add_note` takes its status from it, so a second lock wait cannot fail a call whose note is already written. `Store::read_journal` returns the id of the journal it read, and `Store::commit_to` writes only if the run's journal still has that id. A run that was removed and made again between the two gets nothing (dreamcounter-866f39). A check uses this, because it reads a submission, runs its programs without the lock, and then commits.
  13. **Text, not terms.** Programs and library bodies are s-expression text in the state. dc-mcp does not parse them, or any type text.
  14. **Operator tools only.** The skeleton has `dc_create_run`, `dc_run_status`, `dc_add_note`, and `dc_list_runs`. A run's tasks come from the development corpus (`dc_tasks::families::development`), so the held-out family cannot be named (D14).
  15. **Transport.** MCP over stdio with the `rmcp` crate, version 3.10.
  16. **Refused submissions are counted beside the journal** (dreamcounter-9fa01a, D20 item 5). `Store::commit_or_refuse` either commits events or counts a refused submission. The count goes in the file `refused` in the run's directory: JSON with the journal's id and, for each iteration, the refused repeats and foreign submissions. Under the run's lock the store writes the whole file to `refused.new`, syncs it, renames it over `refused`, and syncs the directory, so a crash leaves the old count or the new one, and a refusal is on disk before it is answered. The file does not grow with the refusals, so a proposer that keeps sending does not grow the run. A file with another journal's id counts as none. So does a file that does not read; the store says so on standard error, and the next refusal writes over it. The journal does not depend on the file. The run setting `max_unchecked_per_batch` was added with a default, so a format-2 journal whose `Created` event lacks it still reads, with the default. The reverse does not hold: a binary from before the setting cannot read a run made by this version, and reports its first record as damaged ("events do not parse"), not as another format. Nothing is lost; read the run with this version.
  17. **Prompt text is stored once** (dreamcounter-20c6e5, D20 item 4). A `PromptStored` event holds a piece of prompt text and its id; ids run 0, 1, ... over the run. A `BatchIssued` event holds its payload in one of two forms. The old form is the payload's JSON text, whole, as a JSON string. The new form is a JSON object: the lease in seconds and the prompt as a list of parts, each either text written out or the id of a stored prompt. The batch number, token and programs wanted come from the event's own fields. The state refuses a `PromptStored` event whose id is not the next one or whose text is already stored, and a `BatchIssued` event that names a prompt not yet stored, and it is unchanged after it refuses one. The state keeps a SHA-256 digest and a length for each stored prompt, not its text, so that a new batch can find a stored prompt by its text. `prompt::PromptTable` reads the events in order, keeps one copy of each stored prompt's text, and gives back each payload: the old form as it is written, the new form as the JSON text of the payload that was sent. The old form still reads and keeps its meaning, so a run with old events goes on, and its new batches use the new form. A new batch names a prompt the run stored before by the digest of its text alone. The state does not hold the text, so the match is not compared byte for byte; a prompt stored earlier in the same commit is compared by its text. A SHA-256 collision would make a payload read back with the wrong text. The format version stays 2, as in item 16. A binary from before this change cannot read a run that has a new event, and reports the record as damaged ("events do not parse"). Nothing is lost; read the run with this version. **Rolling the binary back stops the run:** once a run has issued one batch with this version, it holds `PromptStored` events and a new-form `BatchIssued`, and an older binary cannot replay it at all.
- **Alternatives:**
  - (a) Rewrite a whole state file for each change (write a temporary file, then rename it). The log of payloads and submissions grows with the run, so each change would cost the size of the run.
  - (b) A state file for the small parts and a separate append-only log. A crash between the two writes leaves them out of step.
  - (c) An embedded database (SQLite). It gives the same guarantees with a C dependency and a schema to migrate. A person can read the journal.
  - (d) One long-lived HTTP server. It removes the need for a lock, but someone must start and stop it, and D11 has proposer sessions start their own server.
  - (e) A hand-written JSON-RPC loop in place of `rmcp`. It needs fewer dependencies, but the protocol's version handling would be ours to maintain.
  - (f) Treat only a part line as a torn tail, and any complete bad line as corruption. This was the first version. After a power cut, a record that spans several disk pages can keep its line break and lose earlier bytes. That commit was never acknowledged, but the rule would refuse the run for good.
  - (g) A separate `lock` file in the run directory. This was the first version. A copy of the run that left the empty file out gave a run that was listed but could not be read.
  - (h) Report a set-aside tail on standard error only. This was the second version. An MCP client often does not show standard error, and a closed standard error made the commit panic.
  - (i) Trust the lock alone. This was the second version. A lock on a directory that has been removed does not stop a write to the directory made in its place.
  - (j) Mark a side file as "not yet reported" and have a later commit report it. It covers the case where the tail cannot be put back, but it adds a second kind of state on disk. Writing the tail back needs none.
  - (k) For item 17, store the whole payload once and have a later batch name it. No two payloads are the same: each holds its batch number and token, and the solved programs it shows change with the batch. So the parts that many batches share are stored instead: the instructions around the batch number and token, the language guide, the types, the library, and each task.
  - (l) For item 17, let the first `BatchIssued` that uses a prompt hold it, and later ones point at that batch. A reader would have to take a prompt out of another batch's payload, and the meaning of a batch's event would depend on a later one's use of it.
  - (m) For item 17, find a stored prompt by a key made from what it shows (the library length, the task name). If the prompt code changed between server versions, the key would name text the new version would not send. A digest of the text cannot.
- **Why:** an append-only journal makes each change cost the size of the change. One record for each commit means a crash cannot leave half an iteration's results. The lock makes D11's "many sessions" safe without a daemon.
- **Limits:**
  - **The journal cannot detect a lost tail.** Damage to the end of a journal looks like a torn tail. If the last records are cut off or damaged after they were acknowledged, the store reads a shorter run and reports no error. Nothing in the file says how long it should be. A `Recovery` record or a `torn-*` file after a clean stop is the sign. LevelDB and SQLite's write-ahead log have the same limit.
  - **A lost line break before the last record hides that record.** The scan reads line by line, so the record becomes part of a bad last line, and so part of a torn tail. The same damage anywhere earlier is corruption.
  - **A side file can exist with no `Recovery` record.** Treat the file as the same sign. The commit that made the file did not finish. If the tail is still in the journal, the next commit that writes reports it. No later commit reports it in three cases: the server stopped after it cut the tail off and before its record was on disk, the commit failed and the store could not put the whole tail back, or the commit failed with "outcome unknown".
  - **A commit with no events leaves a torn tail where it is.** Only a commit that writes sets it aside.
  - **A commit over a torn tail holds about twice the tail in memory.**
  - **The directory check covers the wait for the lock only.** After the check, the store works by path. If something outside the store removes the run's directory and makes it again during an operation, a file can land in the new directory. The store itself never removes a run.
  - **Some wiring has no test.** No test fails if `set_aside` stops removing a side file it could not finish writing. The removal itself has a test, and the case was checked by hand on a live server with a file size limit.
  - **A running server checks only the id and the last record.** It does not notice a change to an earlier record that it has already read. It goes on serving and writing. A restarted server refuses the run.
  - **No tool reads log text.** `dc_run_status` shows the count of `Recovery` records. The text is in the journal, and the bytes are in the `torn-*` file.
  - **The lock needs a local file system** with working `flock`. On NFS, Linux emulates `flock` with POSIX locks, which belong to a process, so two stores in one process would both get the lock. The claims on checks (D20) have the same limit.
  - **Reading a run needs write permission** on its journal.
  - **A run records task names only.** If the dc-tasks corpus changes between sessions, the same name means another task.
  - **Seeds above 2^53** are sent as plain JSON numbers. A JavaScript client would round them.
  - **A request line over 16 MiB gets no reply.** `rmcp`'s stdio transport drops it (dreamcounter-62f7f3). Note text has no limit of its own.
  - **The skeleton cannot yet change a frontier, the library, or the iteration over MCP.** The store and the state can. P4.2 and P4.4 add the tools.
- **Costs of the choice:**
  - A server reads the whole journal the first time it uses a run. Since dreamcounter-a27cd4 it reads and applies one record at a time, so it holds a few records in memory. On a 200 MiB journal of 4 MiB records, a cold read grew memory by 8 MiB and took 0.57 s. Before, it grew by 400 MiB and took 1.35 s. There are no snapshots yet, so start-up time still grows with the journal. Add them if start-up time becomes a problem.
  - `Store::log` and `Store::for_each_log` read the whole journal on each call. `for_each_log` holds one record at a time and can stop early. `log` returns all the log's text at once.
  - Each operation reads the journal's header and its last record again.
  - A change to an event's fields needs a new format version and a reader for the old one: the event types refuse unknown fields. A journal with another version gets its own error, not "damaged".
  - `rmcp` brings 39 more packages into the lock file, `tokio` among them. dc-mcp needs Rust 1.89 (`rmcp` needs 1.88, and `File::lock` needs 1.89). The other crates stay at 1.85.
- **Safety rules with no judge:**
  - **`fsync` on real files.** No test fails if the `fsync` calls on real files are removed, because a test cannot cut the power. A test with a stand-in file checks that an append calls sync after the write, and that a failed write or sync is cut out again.
- **Left for later beads:**
  - **P4.2 (dreamcounter-9c8980):** jobs handed out and submissions received need to be events and state of their own, so that `dc_next_batch` and the "quota is in" check do not read the log. A log record now has a kind, an iteration, an optional task, and text.
  - **P4.2:** decide what happens to a submission that arrives after its iteration ended. The state now refuses a log record for another iteration, and D11 needs every submission logged.
  - **P4.2:** a proposer must not reach the operator tools, which show library and frontier sizes. The binary needs a role with its own tool set.
  - **P4.2:** if a tool accepts type text, change the type parser's name map to a seeded hasher first (note on dreamcounter-50338f).
  - **P4.2:** when an event holds a floating-point cost, check that it reads back before it is written. JSON has no NaN.
  - **P4.4 (dreamcounter-86c25d):** evaluation and compression take seconds to minutes and use values that cannot move between threads. Run them outside `commit`, and put `IterationFinished` in the same commit as their results: it fails if another server ended the iteration first.
